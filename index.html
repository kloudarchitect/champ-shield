01

The problem

Automated lending can widen access to credit. As it is usually built, it fails the applicant in four ways at once.

Exclusion
Thin-file applicants are the people a model knows least about, and flexible models shift predicted risk unevenly across groups.
Exposure
Financial and identity data are decrypted during scoring, often on infrastructure the lender does not own.
Opacity
Applicants cannot understand, correct or contest the outcome.
Jurisdiction
Data, model and policy cross borders without proof of authorized control.
02 · 03

Gap, questions and research objectives

Frameworks name the goals. Few name the control that enforces each one, or the evidence that proves it [4].

Research questions

  • RQ1How can CHAMP turn trustworthy-AI principles into enforceable system requirements?
  • RQ2Does the full framework improve safeguards and recourse over a baseline and partial controls?
  • RQ3What does it cost in utility, latency, infrastructure and human-review workload?

Research objectives

  • O1Translate. Turn each trustworthy-AI principle into a control the system enforces.
  • O2Protect. Keep applicant data confidential while it is being processed.
  • O3Include. Widen fair access to credit for underserved applicants.
  • O4Oversee. Give people a real path to review, override and appeal.
  • O5Measure. Show what these safeguards cost in accuracy, speed and effort.

SHIELD reference architecture

Six stages form a loop. Applicant data is in plaintext only inside the attested boundary, which holds stages 03 and 04.

Select a stage. The right-hand column shows what the laptop proof of concept does at that stage.

01 → 02 → 03 → (keys released) → 04 → 05 → 06 → feedback and policy updates → 01  ·  teal outline = attested TEE boundary

A TEE protects one execution boundary: privacy still needs minimization, key management and output controls. Confidential computing follows the definition of the Confidential Computing Consortium, a Linux Foundation project [5]: computation in a hardware-based, attested TEE.

CHAMP traceability: principle → requirement → control → evidence

Each principle is traced to a system requirement, to a control that enforces it at run time, and to the evidence that control emits.

Comparative evaluation and six measured dimensions

Three systems share public credit data and identical models. They differ only in which controls are switched on.

    What is measured

    Economic opportunity
    Approvals among creditworthy thin-file applicants; false-denial rate
    Equity and fairness
    Adverse impact ratio; equalized-odds gap; calibration by group
    Privacy and confidentiality
    Plaintext exposure outside the boundary; features used vs allow-list
    Data sovereignty
    Out-of-policy key releases blocked; valid residency claims
    Human oversight
    Deferral rate; errors corrected per review; minutes per case
    Societal trust
    Decisions reconstructable from evidence; stakeholder survey (planned)

    PoC

    Implementation design: loan agents behind a policy gateway

    A proof of concept implements the governance half of SHIELD on a 16 GB laptop, with synthetic applicants only. It has no TEE, so it says nothing yet about the confidential-computing claims.

    The design rests on three rules. Agents reach tools only through one gateway. The language model extracts and explains, and never decides. Only a human role can commit a decision, within a limit set in policy.

    Components

    Select a component. Two container networks keep agents away from the tool servers: only the gateway sits on both.

    One tool call through the gateway

    Every call from an agent or a person takes these steps, in order. Select a step.

    Why the policy says no

    The policy is one Rego file, evaluated by Open Policy Agent. The default is deny, and a call is allowed only when none of these reasons applies.

    • The tool is not permitted for this identity.
    • The application is outside this session.
    • Bureau consent is not recorded for this application.
    • No recommendation is waiting for a decision.
    • The amount exceeds the sanction limit for this role.
    • A sanctions hit cannot be approved.

    Who is calling

    Each call carries a short-lived signed token. Its subject is the person, its actor is the agent working on their behalf, and it is bound to one application, so an agent cannot read another applicant's file.

    subThe human user, for example a field officer
    rolesThe user's roles
    agentThe agent acting, absent when a person calls directly
    application_idThe one application this session may touch
    trace_idLinks every audit record of one run
    expFive minutes; a token with no expiry is refused

    Least privilege: select an identity to see which tools the policy lets it see. No agent can commit a decision.

    The loan pipeline

    A LangGraph graph runs six agents and then waits for a person. Documents, KYC and credit run in parallel. The run is checkpointed, so the human decision can arrive later, in a separate process.

    Select a node.

    Replay a synthetic application. Each trace is the recorded output of the prototype, run with the models mocked.

      One applicant conversation turn

      A second graph handles the applicant, by text or voice, in English, Hindi, Tamil or Bengali. Every fact in a reply is fixed wording filled from the system of record; nothing is translated at run time.

      Each message passes four steps. Select a step.

      Three models, none with the last word

      extractReads income from a document as JSON. A rule reads it too, and the rule wins if they disagree.
      converseWords the officer's explanation and one optional opening sentence for the applicant.
      guardA safety classifier that gives a second opinion on each message in and out.

      All three are small local models served by Ollama. With the models switched off, the whole system still runs on rules alone.

      What has and has not been tested

      • 83 automated tests pass, covering the guardrail rules, the Rego policy, the gateway's token checks and the simulator servers.
      • All scenarios, the policy refusals and the 31 guardrail self-checks ran end to end with the models mocked.
      • Not yet run: real local models, the container build, and real speech recognition.
      • The non-English wording was written by an AI model and has not been reviewed by native speakers.
      • The self-checks test the guardrails. They do not show that lending outcomes are fair across groups, which needs labelled data and is the job of the A/B/C study.
